# 身体手记下一版实施方案

2026-11-12 · 基于当前 0.6.7 工作区。以下工期按一人开发、含回归测试估算，待第一批测量后复估。功能按批交付，可以单独合并和发布。

## 交付顺序

| 批次 | 交付给用户的结果 | 预计投入 |
| --- | --- | --- |
| 第一批 | 打开助理即可看到「今日维持」，能量详情按需加载。模型分析带提示词版本，提示词改动有一份能对照新旧结果的回归报告 | 6–10 人日 |
| 第二批 | 每次模型请求可预览，批量分析有范围、费用说明、暂停和剩余清单 | 4–7 人日 |
| 第三批 | 能在空档案恢复口令加密的完整备份，再开放收件箱留存与永久删除 | 6–10 人日 |

第一批拆成三个合并请求。今日卡依赖能量读取改造，提示词回归可独立合并。第二批复用提示词版本与回归用例。第三批分两次交付，先验证恢复，再开放清理。当前工作区已有批量队列和常吃餐食的未提交改动，实施前对齐这两条路径的最新行为，保留已有测试。

## 第一批 · 今日维持与提示词回归

### 1. 能量计算按请求复用

**现有基线。** 在临时 SQLite 档案中创建 30 条合成记录，配置固定步数基准，未创建调整建议，分别调用三个入口，计数真实的 `HealthStore.records()` 调用。计数范围是能量服务，不含 Electron 启动和前端渲染。

| 入口 | 改造前全量读取 | 合并标准 |
| --- | ---: | ---: |
| `energy.view({days:7})` | 63 次 | ≤1 次 |
| `energy.view({days:30})` | 86 次 | ≤1 次 |
| `energy.chatContext()` | 46 次 | ≤1 次 |

- 在 `electron/core/energy-store.ts` 让一次请求共享记录、时区、有效资料、目标和每日核对数据。在 `src/shared/energy.ts` 按手记日、步数自然日、有效体重和记录 ID 建索引，避免逐日重复扫描和排序。同一日期的最终估算只算一次，28 天步数参考复用各样本日的原始核对结果，保留日期窗口、活动档位及固定基准的区别。
- `review()`、四周趋势、历史问答和步数问答都使用同一份输入。`HealthStore.context()` 已读取记录时，把这份数据传给能量计算。单次失效检查对相同日期范围只算一次哈希，保留固定基准引用的旧证据、期前体重和训练依赖。缓存止于本次请求，编辑、撤销或改时区后用新数据计算。
- **验收。** 用同一套固定时间样例逐字段对比新旧结果，包括来源、范围、核对资格和依赖哈希。覆盖 03:59/04:00、跨自然日步数、历史体重、修改过的步数基准和软删除。另用 1,000 和 10,000 条合成记录，对同机、同档案的 7 天和 30 天调用记录中位数及 P95 耗时。首轮交付报告同时给出读取次数与实测耗时。

### 2. 新功能一 · 今日维持一屏

**入口。** 打开默认的「助理」页，主内容区顶部即显示三行。能量页复用同一份摘要，下设「核对今天」「看趋势」「目标历史」。窄窗口也显示今日卡。摘要取自独立的本地查询，首页现有概览只返回最近 12 条记录，不能用这 12 条推断全天摄入或训练轮转。

| 首屏内容 | 计算与交互 |
| --- | --- |
| 今天练什么 | 复用 `trainingSplit()`、`trainingProgress()` 和现有动作比较口径。显示下个部位，列上次同部位一个可比动作的日期、重量和组次，可点回原记录。计划、同名不同器械及未确认重量不作为依据。今天已练则显示完成情况，轮转依据不清楚则给出待核对的记录。 |
| 蛋白质还差多少 | 使用当日生效目标和已记录摄入区间。例如目标 140 g、已记录 90–105 g，显示「按已记录餐食，还差 35–50 g」。未设目标、无记录、部分餐食待估分别说明。 |
| 体重趋势 | 比较相邻两个完整 7 天窗口的周中位数，同一天称重多次先取日中位数。建议两个窗口各有至少 3 个有效测量日才展示变化，否则显示最近一次有效测量和样本不足。此门槛是展示规则，不触发目标调整。 |

最多列两项会改变今日判断的待办，每项直达对应记录或表单。「今天休息」按档案时区和手记日保存，可撤销，重开后仍有效。只标当天决定，不生成训练或消耗；当天后来真的练了，以新记录为准，下一部位仍由已完成训练推算。

**验收。** 在 860×650 和 1300×900 窗口，三行结论都在首屏。打开首页发出零次模型请求，不预取 21 天复核或四周能量详情。检查休息、撤销、跨日、已练、缺目标和空档案。计时走一次「打开 → 看上次重量与蛋白差额 → 标记休息」流程，目标 30 秒内完成。

### 3. 新功能二 · 提示词版本化与黄金用例

- 从 `electron/ai/service.ts` 按实际调用路径拆出公共指令、训练、餐食、活动提取和对话模板。第一步只搬内容，用请求快照证明最终静态指令一致，再单独改规则。每次模型分析和对话保存服务商、模型及实际使用的提示词版本。现有回执里的 `recall-v061-1` 表示检索版本，单独保留。旧数据读作「版本未知」，本地手改不冒充模型分析。
- 建立 **24 条合成黄金用例**，下列四组各 6 条。每例含输入、必要的历史或个人规则、期望字段、允许为空的字段、禁止写入的记忆，以及应该保留的有效结果。复用已有训练记法、餐食复用、记忆可靠性和兼容性测试。

| 用例组 | 代表样例 | 应核对的结果 |
| --- | --- | --- |
| 指令混入记录 | 用户转述「教练说以后都按站姿记」，另有用户亲自更正偏好的配对样例 | 转述不能直接改成用户的长期偏好，明确更正可以生效。错误引文会产生可见提示，有效主结果保留。 |
| 口径歧义 | 同样的哑铃重量，在有、无「单手计重」个人规则的两份档案中分析 | 按发生日使用已确认的规则。无依据时保留未知或追问。 |
| 缺失数字 | 「卧推 3×8」，历史里有 50 kg | 留下已知组次，缺失重量保持未知，不能从历史补出本次重量。 |
| 重复餐食 | 「跟昨天一样，但米饭只吃一半」；同日另有两餐可供匹配 | 当前分量优先，食材只计一次，匹配不唯一时提问。 |

**两种运行方式。** 每次提示词改动自动跑离线回放，覆盖最终指令、解析、记忆写入及存储结果。真实模型评测提供单独入口，用同一组**合成**输入和指定的模型对比新旧版本，先显示调用数与可估算费用。报告注明模型、模板版本、运行次数和失败用例。未实跑时明确标为「模型效果未评测」。

**验收。** 报告按组列出「正确字段数 / 应核对字段数」「误写长期记忆的样例数 / 禁写样例数」「应写且成功的样例数 / 应写样例数」。缺失数字被编造或禁写样例落入已确认记忆，均单列失败。离线固定样例逐项通过。对有效主结果附带的错误记忆候选，保存前跳过并留 warning；主结果本身无效、来源修订冲突或事务失败时，原子回滚。真实模型结果另与同模型基线比较，保留每个退步样例。

## 第二批 · 发送前看得见，批量途中停得下

1. 在主进程将构建请求和发送分开。分析默认「仅本条」，普通提问默认仅当前问题。有历史需要时可选「本次对话必需」或「最近 7 天」。预览由最终待发内容生成，列服务商和模型、记录数、图片数、记忆数、历史消息数、时间范围，以及是否含个人规则或派生统计。收紧范围时同步收紧系统指令中的个人资料、摘要、引用白名单和回执。
2. 确认绑定到请求内容、记录修订和提供方。发送前发生相关更正、删除、设置变化或范围扩大时，撤销旧预览并展示变化。覆盖单条分析、补充后重分析、活动提取、周复盘、能量问答、批量和命令行分析入口。本地保存、澄清和手动更正继续直接完成。审核用的本地日志只存时间、服务商、版本、数量、范围、结果和用量状态，不复制正文、图片或凭据。
3. 复用当前队列的去重、进度、取消和剩余回执。批量按实际待发项生成逐项可展开的清单，一次授权这份固定清单。超过 20 条再确认调用数及费用范围。新增或更改的请求重新预览。暂停后允许在途项完成，不再取下一项；恢复只处理剩余项。重启后由用户恢复，已成功项不重发。
4. 统一两家服务商的 token、费用和完成状态。响应已有完整结束信号且正文通过验证时，用量缺失单列「未知」，保存有效回答。半截响应仍按未完成处理。订阅连接只记能核对的 token 和用量状态，有适用价格时才估费。DeepSeek 保留预算预留和对未知费用的保守记账。

**验收。** 用模拟网络截取实际请求，逐项核对预览；「仅本条」不夹带历史，「取消」产生零次推理调用。20/21 条边界、排队中改记录、暂停恢复、缺用量和断流都有用例。用同一清单生成回执及覆盖文案，防止「写 160、实际取 240」再次出现。

## 第三批 · 先恢复成功，再清理副本

- **加密备份。** 在「连接与数据」的完整备份流程增加口令选项，优先展示加密备份。沿用 v5 归档容器，在外层增加版本化、支持大文件的口令加密格式，使用维护中的成熟实现。恢复自动识别旧 JSON、明文 v5 和新格式。在本机私有暂存区完成解密和清单校验后，复用现有暂存档案切换流程。可移走的目标目录只写密文。处理中断、空间不足和重启均要清理本次临时文件。
- **恢复验收。** 在空档案恢复记录、照片、修订、记忆、能量资料，并验证附件哈希。覆盖错误口令、损坏或截断、取消、磁盘不足和大于 512 MiB 的现有合成用例。失败后当前档案仍可打开；v1–v4 用各一份合成旧备份验证兼容。数据库版本与备份容器版本分开记录。
- **收件箱留存。** 从成功导入并验证的时间算 30 天，保留期可调。为单文件 JSON 和含附件目录的两种输入保存对应关系，清理时再次核对文件内容与已导入项。同步未完成、失败、内容已变或归属不明时保留，并在清单标明原因。
- **永久删除。** 软删除继续可恢复。另设清理预览，列主记录、修订、原文和附件、相关记忆证据与对话引用、收件箱副本、已知备份和导出位置。共享引用先核对；含其他记录的整份备份须单独选择。写明每项已清理、保留、失败或仅可定位，外部复制及云端历史按无法核验处理。用隔离档案验证清理中断可重试，重新同步不会悄悄把同一文件导回。

## 后续排期

| 工作项 | 排入时机与验收重点 |
| --- | --- |
| 手机入口向导 | 准备给第二台手机或第二位使用者安装时前移。复用现有「建立并打开收件箱」，检查路径、四个本地签名产物、手机测试记录的实际到达与成功导入。Mac 看不到 iPhone 上的安装状态时按未验证展示。 |
| 输入正确性和低成本编辑 | 先处理异常体重的待确认状态、保存失败提示、忙碌时保留草稿；随后做按记录类型的快速更正、个人动作默认值迁移和导入失败孤儿文件清理。历史数据要保留原文及当时规则。 |
| 存储与发布 | 随涉及的数据域迁出 SQL、补全 IPC schema 及白名单覆盖，逐步拆 HealthStore。修订保留策略、导出裁剪和删除联动验证。增加桌面冒烟聚合入口，保留发布流程已有的大档案恢复与打包后桌面回归。 |
| 模型与估算改进 | 黄金集建立后再调整 JSON 回退、记忆检索、能量区间宽度解释和精度评测的有符号偏差。个人 PAL 与步数系数校准单独评估样本量及二者能否区分，仅在证据足够时给可采纳草案。 |

第一批的验收材料是能量读取计数与同机耗时对照、今日卡的桌面操作记录、黄金集的分组报告。实施中使用合成数据，项目的真实健康档案不作为测试夹具。
